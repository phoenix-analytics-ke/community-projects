# DAY 10 PULL REQUESTS

In the words of the GitHub Docs, a pull request is a means to propose, review, and merge code changes into a project. 

On submission, responsible parties will review your changes for approval, make comments, and merge to codebase. This is the beloved code review, so many great memories. It allows owners to maintain project quality and reduces the risk of integrating issues into the main project before merging proposed changes.

## Requirements for creating pull requests:

Permissions? 

You must have the appropriate access to the original repository if you plan to contribute herein. I.e. for a shared repository workflow, you need write access to the source branch and read access to the destination branch.

If you are contributing via a fork, you do not need write access to the original repository. This is the standard open-source workflow: 

- fork the original repository on GitHub.

- clone your fork locally.

- create a feature branch in your fork.

- push that branch to your fork.

- open a Pull Request from your forked branch to the original repository’s target branch (usually main).

You can set up upstream locally to sync your fork with the original repository with

`git remote add upstream https://github.com/original-owner/repo.git`

This helps you fetch and merge updates from the original repository into your fork, but it is not required to create a PR.

When opening a Pull Request:

Source = your-username:feature-branch

Target = original-owner:main

You only need:

- Read access to the original repository.

- Push access to your fork.

No special permissions are required on the upstream repository to open a PR. The maintainers decide whether to review and merge it.

Review more on pull requests in this guide. https://www.hackerone.com/blog/pull-requests-101
