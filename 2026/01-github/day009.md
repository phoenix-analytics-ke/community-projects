# DAY 9 FORKS, CLONES & STREAMS
Today we revisit workflows along side forking and cloning. Imagine you are onboarded to work on a project and a task exists as an issue for example that you are required to resolve. You are not the owner of this repository, but require a copy of this repo in order to complete your task.  

Enter git clone and git fork. 

Forking creates a server-side copy of a different user’s repository on GitHub. This fork contains the full history and branches of the original repository but is fully independent. Changes made to your fork do not affect the original repository unless a Pull Request is opened and merged. Post forking, you can modify the copy of this repository without affecting the original repository. 

Cloning on the other hand creates a local copy of a remote repository on your machine. Running git clone <some_url> on CLI will effectively download the repo contents to your device. That includes the entire repository history, initializes a local repository, and configures a remote named origin pointing to that URL. 

So, question, if you fork a repository and then run git clone <url_from_your_account> and make some changes, which repository will change? Which repository will change?

## Step2: Clone the forked repository

Go to your fork on GitHub and click the green code button to get the repository URL.

Open bash and in your terminal run git clone <your_repository_url>.

Enter the directory with the files with cd Spoon-Knife/ 

Inspect your remote repositories with git remote -v and check your branches with git branch --list

Git automatically set origin. origin points to your fork. We know this because git remote -v returned your remote aliases. At this point running git pull, git fetch, or git push will retrieve updates from or send changes to your copy of the repository. Notice there is no upstream yet.

Pause. What is an upstream?

In distributed version control, development does not flow in a single straight line. Instead, changes move between repositories in structured directions. These directional flows are what we informally call streams. There are two primary streams in a fork-based workflow:

- Upstream - the original source repository
- Downstream - your fork (or any derivative copy)

The upstream repository is the authoritative source of truth. The downstream repository is a copy that can diverge, evolve, and eventually propose changes back upstream. Streams describe where changes originate and where they are sent. In open-source environments for example, you do not have write access to the upstream repository. Instead, you:

- Fork it (creating a downstream copy)
- Clone your fork locally
- Push changes to your fork
- Propose those changes upstream via Pull Request

So streams define permission boundaries and flow direction.

## Step4: Add the upstream remote

Let’s understand why we would do this in the first place. By connecting your local repository to the original project, you can receive updates from it.

git remote add upstream https://github.com/octocat/Spoon-Knife.git

This will add ANOTHER remote reference to your local repository. Run git remote -v to confirm this. 

Now your local repository knows about:
- origin - your fork
- upstream - original project

You can contact the remote repository to update upstream/main NOT origin/main.

Run git fetch upstream then git branch -r
